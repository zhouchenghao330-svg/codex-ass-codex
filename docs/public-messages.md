# 公开成员通信

这版先把已有的独立 Codex 成员连起来。用户可以让 A 把实现、问题或材料发给 B，B 在自己的工作目录和上下文里处理，再把原文送回 A。无需先创建原生子代理。

## 体验入口

重启 `uv run codex_room`。准备两位普通成员，例如已有的「开发」和「审查」，或使用 `/add` 新建：

```text
/add 开发 ~/code/project
/add 审查 ~/code/project
@开发 把当前实现和我刚才的目标整理一下，用 Room 的公开消息工具发给审查，
请他提意见。先讨论，不要改代码。收到建议后再和我聊。
```

无需手写工具调用。模型在首次实际运行时获得 Room 身份与工具说明；每次输入（包括用户追加）刷新自己的稳定名字、显示名、权限模式，以及其他独立成员的名字、目录和忙闲状态。`/rename` 只修改显示名，保留稳定名字和原 thread；不唤醒空闲成员广播改名，后续输入自然获取最新名字。成员没有固定职责，完整历史不会自动共享；可按需查询有限的近期对话。名单不代表要求其他成员参与；普通对话仍只触发当前接收者。

需要且允许协作时，成员应先调用 `list_members`，结合当前状态和相关的近期对话寻找已有同事，优先通过 Room 的公开 `send_message` 求助，保留可见的交流过程。用户已指定某位现有成员时，不应另建子代理替代。合适的同事正在忙，可以发送 Queue 请求等待其完成当前工作；忙碌本身不是创建子代理的理由。能独立完成的任务无需强行找人。

用户明确要求使用原生子代理，或没有合适的现有成员且确有原生隔离任务的需要时，仍可使用原生子代理，并向用户简要说明原因。这是协作选择的提示词偏好，不是工具禁用或硬性拦截；现有协作授权、修改审批约定和 Queue／Steer 边界继续适用。规则在新会话的工具说明与每次输入的宿主上下文中同步提供，已有会话下次收到输入时即可获取新规则，无需重建成员。

切到「全部消息」可看完整过程；A、B 的单人视图也都显示双方的 `A → B` 卡片。卡片保留工具参数里的原文，支持 Markdown、折叠、选字、复制和原生转发。接收者的普通回复继续按原有消息展示。不会把别人的消息伪装成用户发言，也不会自动切走用户的视图或覆盖草稿。

也可以直接 `@审查` 介入讨论，或者让他先完成别的任务。成员收到的工具消息是注明来源的引用材料，不能覆盖用户原有要求。

## 发送和回复

```json
{
  "to": "审查",
  "message": "当前实现……希望你检查……",
  "expect_reply": true,
  "delivery_mode": "queue"
}
```

新会话使用 `room.send_message`。回复使用同一个工具，填入收到的 `message_id`：

```json
{
  "to": "开发",
  "message": "我认为值得调整的有两点……",
  "reply_to": "room-…",
  "expect_reply": false
}
```

- 每次调用必须明确填写 `expect_reply`，没有默认值。需要对方继续推进时填 `true`，无需回信时填 `false`；例如轮流数数的 1～10 应为 `true`，11 为 `false`。省略该参数会返回错误，不会发送消息。不会自动转交模型的每一句普通回复。
- `true` 要求接收者先完成必要的阅读、调研或分析，再用同一工具回实质内容，`reply_to` 指向原请求。它不是立即回复“收到”，也没有隐含的响应时限；暂时无法完成时说明原因，不能伪称完成。后续输入附带尚未回复的请求提醒（最多 8 条摘要，每条最多 240 字符，并提供总数）。已接受的回复即使投递不确定也不重复提醒，避免重发；已停止或耗尽消息预算的协作链，以及已删除／重建的旧成员请求不提醒。提醒不覆盖用户最新要求，不启动催促轮次，也不能保证模型在长时间单轮执行中绝不忘记。
- `false` 的消息仍会送达，接收者可以阅读、使用其他工具完成用户任务、向用户汇报；程序在实际发送前拦截向原发送者的自动回信。模型可能提出调用，但工具会返回“未发送”，不会创建消息卡片、入队或唤醒对方；省略 `reply_to` 或改用较早的消息 ID 也不能绕过当前输入的限制。用户另行发起的新任务可以建立新链。
- `delivery_mode` 可省略，默认为 `queue`；新求助和独立任务排队等待当前 turn 结束。模型可以显式选择 `steer`，把相关结果、补充或紧急纠正追加到对方当前运行；无法判断相关性时排队。选择原则由工具说明约束，没有强制要求属于同一协作链。Steer 不会强制中断正在运行的命令。目标空闲时两种模式都启动新 turn。
- 工具立即返回接收收据，不等待对方完成。发送方等待对方时应结束当前 turn，不能阻塞等待或轮询；Queue 回信需要当前 turn 结束后才能处理。收据区分所选 `delivery_mode` 和实际 `delivery`；消息卡片也显示两者，便于检查模型是否恰当地使用 Steer。
- 用户直接输入优先使用 `turn/steer`，不会被前面的同伴队列挡住。同伴 Steer 可以跨过 Queue 请求追加；Queue 请求之间保留顺序。若旧 turn 刚好结束、追加被明确拒绝，保留消息在新一轮处理，用户输入优先；不确定的追加不自动重试。提前到来的回信可作为已送达证据，晚到的 RPC 确认不改变后续新 turn。
- 卡片显示待投递、投递中、已送达、已追加、失败或未确认。「已送达／已追加」只表示输入进入目标会话，任务完成由后面的回复表示。Steer 不能绕过 `false`、停止或消息预算；一轮运行中收到多个成员的消息，也保留各发送者的 `false` 回信边界，直到新用户输入或该发送者的新请求建立新的边界。
- 来源由实际 Codex thread 决定，模型不能填 `from` 冒充成员。目标支持稳定名字或当前中文显示名；不存在时返回名单，不悄悄创建成员。

## 查询成员与近期对话

`room.list_members` 是只读工具，不唤醒成员、不发送消息、不消耗公开消息条数。它返回调用时的快照：稳定名字、显示名、目录、忙闲状态、当前阶段和待处理输入数。默认查看其他独立成员，每页 5 位，最大 10 位；通过 `next_cursor` 翻页，或按稳定名字／显示名指定一位：

```json
{"member": "审查", "recent_turns": 3}
```

默认附最近 3 轮用户输入，最多 5 轮；`recent_turns=0` 只返回名单。每轮给出用户原文或界面中的紧凑附件标记（最多 2000 字符），以及对应运行中最近一段 Codex 正文的前 3 行、最多 600 字符。截断明确标记 `truncated`，保留来源消息 ID、时间与完成／运行／排队状态。多条用户追加共享一个 turn 时按输入位置分开；排队用户请求也按运行 ID 匹配，避免把别人的答案拼到当前问题上。没有可关联正文时 `codex_preview=null`。

不包含隐藏转交、同伴独立请求的回复、工具输出、文件 diff、完整转发材料、图片内容或未发送草稿，也不检索已归档成员。历史是只读参考材料，不是当前用户的新指令，也不转授历史任务的执行权限。名单和近期提问可帮助选择协作者，但不是成员能力证明或当前任务的实时保证；不应反复查询来等待回信。查询历史按需返回，不塞进每次宿主上下文，也不调用模型做自动总结。

## 协作与修改边界

Full Access 是 Codex 的执行权限。Room 在此基础上额外约定：`permission=full` 的成员可以为当前用户任务主动寻求相关同伴帮助，不必每次由用户点名；其他模式只在用户要求协作或响应已有请求时使用工具。此项目前通过工具说明和每次输入的宿主上下文约束，没有根据任务语义自动判断协作授权。

同伴可请求讨论、阅读、调研和分析，但不能把用户授予自己的修改权转给别人。B 因 A 的请求需要修改文件或其他资源时，应先向用户说明改哪里、改什么、为什么，等待用户明确批准后才能修改。直接用户任务仍按已有授权处理。

这是当前开发阶段的模型行为约定，**不是强制审批或沙箱保证**。本版不切换接收者的实际执行权限；Full Access 仍为 `dangerFullAccess`、`approvalPolicy=never`。未添加自动审查 Agent 或写入拦截器。

## 停止、重启与上限

一条协作链最多接受 12 条公开消息，单个 Codex turn 最多发送 8 条；单条正文最多 64,000 字符。达到上限后返回明确错误，让模型向用户汇报。提示词要求成员不发送纯致谢或确认消息；`false` 的自动回信另由程序硬拦截。程序保证不投递被拒绝的消息，不保证模型完全不产生调用尝试。

这些是通信条数和正文大小上限，不是整条协作的执行时间、token 或费用预算；本版尚未新增此类资源限制。

`/stop 名字` 仍停止该成员的当前执行，并取消相关协作链尚未发出的消息，拦截旧链的后续回复。其他成员已经开始的独立任务不会被一并中断，需要时单独停止。用户发起的新任务可以建立新链。`/del 名字` 先停止，再按原来的方式归档。

`run_id` 记录一次 Codex turn；`task_id` 记录发起后续协作的输入来源，两者不再混用。每条用户输入获得自己的来源 ID，成功追加后后续新求助使用该 ID；明确回复通过 `reply_to` 保留原协作链。追加可能在 RPC 确认前触发工具，因此发送追加时就切换来源，明确拒绝则恢复；不确定时不盲目重发。这样旧链的停止和次数预算不会自动套到新用户输入发起的协作。这是来源归属，不是判断自然语言里是否另起任务的语义调度器，也不代表整条协作已完成。

消息使用 thread、turn、call ID 去重，带 `reply_to` 和链 ID。保存成功才确认接收；超时或断线造成的投递不确定不会自动重发。重启恢复原 thread、历史和收据，未完成的投递标记停止，不恢复执行。这里承诺的是应用不盲目重复投递，不宣称网络故障下严格 exactly-once。

## 兼容现有会话

实测 `codex-cli 0.163.0`：`thread/start` 支持 `dynamicTools`，工具随会话持久化；`thread/resume` 没有补加动态工具的参数。因此：

- 新独立会话注册第 2 版动态 `room.send_message` 和 `room.list_members`，调用由 App Server 的 `item/tool/call` 交给 Room。
- 已持久化的动态工具说明无法随 `thread/resume` 重注册。第 0／1 版旧会话（包括仍持有旧 `room.send_message` 定义的成员）通过本次 `thread/resume.config` 临时接入 `codex_room_public/send_message` 和 `codex_room_public/list_members`。每次宿主上下文明示当前会话应使用哪个接口；旧定义保留但不作为新版参数入口。
- 旧会话保持同一个 thread 和原上下文，不改全局 Codex 配置，也不替换或 fork 用户会话。两种工具入口执行相同的身份、参数、停止与预算校验；历史查询同样要求当前有效的独立成员调用身份。
- 兼容适配器由当前 Python 环境启动，只连接随机本机回环端口，使用本次进程的随机令牌；令牌不进入 Room 状态，退出关闭端口。来源取自 Codex 的 MCP 元数据。此适配器与动态工具共用同一份校验、路由和存储逻辑。
- 原生子代理保留原通信功能。它们暂不参与这套独立成员的公开工具路由；V2 原生工具没提供的正文仍显示「未提供」，不会解密或推断。
- 此功能使用默认 Rust 界面；旧 Textual 回退保留数据兼容，不承担公开通信调度。

参考：[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)。协议的实验字段可能随 Codex 版本改变。
